# 阶段二范围修正：服务层增强与可观测性补全

## 1. 结论

阶段二由 **“服务化补全”** 调整为 **“服务层增强与可观测性补全”**。

调整后的阶段二只做一件事：**让已经存在的 FastAPI 服务层变得可追踪、可诊断、可防护，并为后续 Harness、多 Agent、缓存预留协议字段**。

---

## 2. 调整理由

1. **起点不同**：基础项目已有 `app.py`（`/chat`、`/chat/stream`、`/webhook/{platform}`、静态页）、`static/index.html`、`Dockerfile`、`docker-compose.yml`、`deploy/nginx.conf`。原“补服务层/补前端”的前提不成立。
2. **主要矛盾不同**：现状不是“没有接口”，而是“接口缺少可观测性与工程化防护”——无请求 ID、无结构化日志、无统一错误、无健康检查、无限流、无协议元数据。
3. **避免重复建设**：从零重写会丢弃已有的 NDJSON 流式、会话读写、转人工与 Mock 兼容逻辑，风险高且无收益。
4. **为后续阶段铺路**：阶段三需要 Tracing 接入点，阶段四需要路由透出字段，阶段五需要缓存命中字段。阶段二先把协议与错误边界定义好，后续只填充实现，不反复改协议。
5. **边界纠偏**：原阶段二描述中的“可被压测”属于阶段六，不应作为阶段二交付条件。

依据：`docs/baseline/project-structure.md` 第 7 节、第 8.3 节（Web/接口缺口）、第 8.8 节（可观测性缺口）。

---

## 3. 阶段二不做什么

| 不做项 | 原因 |
| --- | --- |
| 不从零重写 `app.py` 或替换 FastAPI 结构 | 现有服务层可复用，重写会破坏已验证的对话与流式链路 |
| 不替换现有 NDJSON 流式协议 | 前端已按 `{"delta": ...}` / `{"done": true}` 实现，替换会造成兼容性回归 |
| 不重写 `static/index.html` 技术栈 | 原生 HTML/JS 已可演示，阶段二不迁移 Gradio/React，也不做大规模 UI 改版 |
| 不实现多 Agent、Router、工具子集隔离 | 属于阶段四；阶段二最多预留 `agent` / `route` 字段 |
| 不实现 Harness 运行时（Tool Registry、Context Assembler、Loop Controller、Retry/Fallback、Tracing 实现） | 属于阶段三；阶段二只建立请求 ID、日志与异常包装接入点 |
| 不实现 Redis TTL、会话状态缓存、语义缓存 | 属于阶段五；阶段二不改变 `memory.py` 的存储语义 |
| 不实现评测与压测 | 属于阶段六 |
| 不实现完整的 Webhook 签名算法 | 阶段二只输出策略与配置占位；真实接入需平台密钥与回调环境 |
| 不实现完整鉴权与账号体系 | 涉及产品策略、密钥管理与用户模型；阶段二只做基础限流，鉴权作为独立安全项另行评估 |
| 不引入新的重型框架或新依赖 | 优先使用 Python 标准库与 FastAPI 现有能力，控制改造面 |

## 4. 阶段二要做事项

### 4.1 范围条目

| 编号 | 范围条目 | 对应基线条目 | 交付边界 |
| --- | --- | --- | --- |
| P2-1 | 请求 ID 与结构化日志 | 8.8 可观测性 | 每个请求生成/透传 `X-Request-ID`；输出 JSON 日志，包含请求 ID、路径、状态码、耗时、会话 ID（脱敏） |
| P2-2 | 统一错误响应与异常兜底接入点 | 8.3 接口、8.8 可观测性 | 定义统一错误体；增加全局异常处理；在工具/LLM 调用边界建立可替换的异常包装点；**不实现重试与降级策略** |
| P2-3 | 健康检查与基础运行防护 | 8.3 接口 | 增加 `/healthz`；支持可配置 CORS 白名单；增加进程内基础限流；不引入 Redis 限流或多实例一致性 |
| P2-4 | NDJSON 流式协议字段预留 | 8.3 接口、8.8 可观测性 | 在保持 `delta` / `done` 兼容的前提下，新增 `meta` / `tool` 事件类型与 `agent`、`tool_calls`、`latency_ms`、`cache_hit` 可选字段；阶段二只填请求 ID 与总耗时，其余留空或默认值 |
| P2-5 | Webhook 验签策略与配置占位 | 8.3 接口 | 明确各平台验签策略、配置项与失败行为；阶段二不实现真实签名算法，不接入平台密钥 |

### 4.2 协议预留的最小定义

阶段二只定义结构与兼容规则，不承诺字段一定有业务值：

| 字段/事件 | 阶段二行为 | 后续填充阶段 |
| --- | --- | --- |
| `meta` 事件 | 流开始时发送，包含 `request_id`、`session_id`、`protocol_version` | 阶段三补 tracing；阶段四补 `agent` / `route` |
| `agent` | 预留，默认 `null` 或 `"single"` | 阶段四由 Router 填写 |
| `tool_calls` | 预留数组，默认空数组 | 阶段四补工具轨迹；阶段三补工具耗时/状态 |
| `latency_ms` | 流结束时给出服务端总耗时 | 阶段三拆分 LLM/工具/存储耗时 |
| `cache_hit` | 预留布尔值，默认 `false` | 阶段五接入会话/语义缓存后填写 |
| `tool` 事件 | 预留事件类型，阶段二可不发送或仅发送空样例 | 阶段四发送真实工具调用事件 |
| `error` 事件 | 与统一错误体保持一致的结构 | 阶段三接入 Retry/Fallback 后补充错误分类 |

兼容要求：

- 现有客户端只读取 `delta` / `done` 时行为不变；
- 新增字段均为可选，未知字段可被忽略；
- 不改变 HTTP 状态码语义（正常对话仍为 200，流内错误用 `error` 事件表达）。

### 4.3 非功能约束

- 日志不得输出 API Key、完整订单号、完整手机号等敏感信息；会话/订单标识需截断或哈希。
- 所有新增配置通过环境变量提供，并有安全默认值（默认关闭 CORS 通配、默认开启基础限流）。
- 限流为单进程内存实现，明确标注“仅本地开发/单实例”，不作为生产级方案。
- 所有改动保持增量、可回滚，不改变现有业务工具的返回结构。
- 不修改 `docs/baseline/` 下已有文档；如需修正基线结论，另建文档说明。

---

## 5. 阶段二验收口径

- 每个请求都能通过 `X-Request-ID` 在日志中定位；
- 工具/LLM 异常返回统一错误体，不泄露堆栈与密钥；
- `/healthz` 可返回服务与存储类型状态；
- CORS 与限流按配置生效，默认配置下不影响现有前端；
- `/chat/stream` 在新增 `meta` / `done` 字段后，旧前端仍可正常渲染；
- 协议字段、错误体、配置项有文档说明；
- 不引入多 Agent、Harness 运行时、Redis 双层缓存、评测压测的实现。

## 6. 与后续阶段的衔接

### 6.1 协议预留字段的消费方式

- **阶段三（Harness Tracing）**：
  - 使用 P2-1 的 `request_id` 作为 trace 主键；
  - 在 P2-4 的 `meta` / `tool` 事件中填充工具名、参数摘要、耗时、成功/失败；
  - 将 `latency_ms` 拆分为 LLM、工具、存储三段耗时，事件结构不破坏。
- **阶段四（多 Agent 路由）**：
  - 在 `meta` 中写入 `agent` 与 `route_reason`；
  - 在 `tool_calls` 中记录子 Agent 实际调用的工具子集；
  - 前端沿用同一协议展示“由哪个子 Agent 处理”，无需再次改协议。
- **阶段五（Redis 双层缓存）**：
  - 填充 `cache_hit` 与缓存类型（session / semantic）；
  - 复用 `latency_ms` 对比缓存前后延迟；
  - 不改变事件结构。

### 6.2 错误与异常接入点的接管方式

- 阶段二定义：
  - 统一错误体（`code`、`message`、`request_id`、`retryable`）；
  - 工具/LLM 调用的异常包装函数或装饰器位置；
  - 错误分类枚举（参数错误、工具失败、LLM 超时、内部错误）。
- **阶段三（Retry / Fallback）**：
  - 在既有包装点内部增加重试策略、超时与降级回复；
  - 复用 `retryable` 字段决定是否重试；
  - 不改变对外错误体结构，只补充错误码与兜底文案。
- 阶段二**不实现**重试、熔断、降级回复，避免与阶段三重复。
