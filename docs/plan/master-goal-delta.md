# 《总项目实现目标》差异修正清单

## 0. 使用说明

- 本文档**不重写**《总项目实现目标》，只列出需要修正或补充的条目。
- 依据：`docs/baseline/project-structure.md` 第 7 节（现状差异）与第 8 节（缺失项清单）。
- 每条修正按“原文表述 → 实际现状 → 修正后表述 → 修正理由”四要素记录。
- 编号 `D-xx` 仅用于后续文档引用，不改变原文章节结构。

---

## D-01 第 3.2 节：Web 服务层现状

**原文表述**

> | Web 服务层 | 缺失 |

**实际现状**

- `app.py` 已提供 FastAPI 服务：
  - `POST /chat`（非流式）
  - `POST /chat/stream`（NDJSON 流式）
  - `POST /webhook/{platform}`（平台回调入口）
  - `GET /` 与 `/static`（静态页与资源）
- 启动时按环境变量选择 `LLMClient` / `MockLLM`，并按 `REDIS_URL` 选择 SQLite / Redis 记忆。
- 但缺少：鉴权、限流、健康检查、请求 ID、结构化日志、统一错误响应、Webhook 验签、路由/工具/耗时等协议字段。

**修正后表述**

> | Web 服务层 | **已有最小 FastAPI 实现**（对话、NDJSON 流式、平台 Webhook、静态页）；缺少鉴权、限流、健康检查、请求 ID、结构化日志、统一错误响应、Webhook 验签与可观测协议字段 |

**修正理由**

基础项目不是“无服务层”，而是“可运行但未工程化”的最小服务层。阶段二应从增强开始，避免重复实现已有接口。

## D-02 第 3.2 节：前端界面现状

**原文表述**

> | 前端界面 | 缺失 |

**实际现状**

- `static/index.html` 已存在单页聊天界面：
  - 原生 HTML/CSS/JS，无构建工具；
  - 调用 `/chat/stream`，解析 NDJSON 并逐块渲染；
  - 维护 `session_id` 并发送多轮消息。
- 但缺少：路由 Agent、耗时、缓存命中展示；无错误态/重连/消息重发；无组件化与前端测试。

**修正后表述**

> | 前端界面 | **已有极简单页前端**（原生 HTML/JS + NDJSON 流式渲染）；缺少路由/耗时/缓存展示、错误态与可维护性建设 |

**修正理由**

阶段二不应从零写前端；后续只需在现有页面上增量展示服务端新增的元数据，保留现有技术栈可降低风险。

---

## D-03 第 4 节：最终目标第 1 条“服务化”

**原文表述**

> 1. **服务化**：使用 FastAPI 提供 HTTP / WebSocket 或 SSE 对话接口，支持多轮会话、流式输出和 Agent 路由结果展示。

**实际现状**

- FastAPI 与多轮会话、NDJSON 流式输出已存在。
- 尚无 WebSocket/SSE，也无 Agent 路由结果。
- 服务层缺少稳定性与可观测性能力（见 D-01）。

**修正后表述**

> 1. **服务层增强**：在现有 FastAPI + NDJSON 流式接口基础上，补齐限流、健康检查、请求追踪、统一错误与协议元数据；鉴权作为后续独立安全项评估；WebSocket/SSE 作为可选演进，不作为阶段二必做项；Agent 路由结果在阶段四接入。

**修正理由**

把“从零补服务层”改为“增强现有服务层”，与基线第 8.3 节对齐；同时避免在阶段二提前引入多 Agent 路由。

---

## D-04 第 4 节：最终目标第 2 条“前端可演示”

**原文表述**

> 2. **前端可演示**：提供极简前端，能够发送消息、展示回复、展示本次请求由哪个子 Agent 处理，以及关键耗时和缓存命中信息。

**实际现状**

- 极简前端已存在，可发送消息、展示流式回复。
- 尚不能展示子 Agent、耗时、缓存命中；原因是服务端协议中还没有这些字段。

**修正后表述**

> 2. **前端增强**：在现有 `static/index.html` 上增量展示子 Agent、耗时、缓存命中与错误状态；保留原生 HTML/JS 技术栈，不重写前端。

**修正理由**

前端的缺口是“展示字段缺失”，不是“页面缺失”；阶段二先做协议预留，展示能力随阶段四/五逐步接入。

---

## D-05 第 8 节：阶段二名称与范围

**原文表述**

> ### 阶段二：服务化补全
>
> 为纯逻辑 Agent 核心补 FastAPI 服务层和极简前端，使系统可对话、可演示、可被压测。

**实际现状**

- FastAPI 服务层与极简前端均已存在，系统已可对话、可演示。
- 当前主要缺口是服务层工程化与可观测性，而不是“缺服务层”。
- 压测体系属于阶段六，不应作为阶段二的完成条件。

**修正后表述**

> ### 阶段二：服务层增强与可观测性补全
>
> 在现有 FastAPI 服务层与静态前端基础上，补齐请求 ID、结构化日志、统一错误响应、健康检查、基础 CORS/限流、NDJSON 协议字段预留与 Webhook 验签策略；不重写既有服务层与前端。

**修正理由**

名称与范围必须反映真实起点；否则后续步骤会重复实现已有接口，且容易把阶段三至六的内容错误地并入阶段二。

---

## D-06 第 3.2 节：记忆存储现状的完整性

**原文表述**

> | 记忆存储 | 已有 SQLite / Redis 两种实现 |

**实际现状**

- SQLite 与 Redis 两套会话历史实现均存在，且已本地验证读写。
- 但两者都只是“历史消息列表”：
  - Redis Key `chat:{session_id}` 无 TTL；
  - 无租户/会话隔离前缀；
  - 无会话状态缓存、无语义缓存；
  - 无缓存命中统计。

**修正后表述**

> | 记忆存储 | 已有 SQLite / Redis 两种**会话历史**实现；缺少 TTL、多租户隔离、会话状态缓存与语义缓存（阶段五） |

**修正理由**

原文容易让人误以为“缓存能力已具备”。明确其仅覆盖历史消息，可避免阶段二重复实现，也避免阶段五遗漏 TTL 与语义缓存。

---

## D-07 第 3.2 节：工具层现状的完整性

**原文表述**

> | 工具层 | 已有工具定义 |

**实际现状**

- `agent.py` 中硬编码了 6 个工具 schema。
- 无声明式注册表、无启停开关、无按 Agent 分配工具子集、无工具执行指标。
- 工具异常未统一捕获。

**修正后表述**

> | 工具层 | 已有 6 个**硬编码**工具定义；缺少 Tool Registry、启停与按 Agent 分配、统一异常与调用指标（阶段三） |

**修正理由**

工具“存在”不等于“可治理”。明确硬编码现状，才能解释阶段三引入 Harness Tool Registry 的必要性。

---

## D-08 第 7 节：目标架构的起点标注

**原文表述**

> 前端（Gradio / React）→ FastAPI 服务层 → Agent Harness Runtime → 多 Agent 编排层 → 工具与数据层

**实际现状**

- 当前已有：原生 HTML 前端、FastAPI 服务层、单 Agent、工具层、数据源、SQLite/Redis 历史。
- 当前没有：Harness Runtime、多 Agent 编排层、双层缓存、评测压测。
- 目标架构本身不变，但需要明确“哪些是存量、哪些是增量”。

**修正后表述**

> 保留原目标架构；在图中标注：**原生 HTML 前端、FastAPI 服务层、单 Agent、工具/数据源为存量模块**；**Harness Runtime、多 Agent 编排、Redis 双层缓存、评测压测为增量模块**。前端技术栈不强制迁移到 Gradio/React。

**修正理由**

避免把目标架构误读为“全部新建”，也避免阶段二重复实现存量模块；前端技术栈的表述需与实际资产一致。
