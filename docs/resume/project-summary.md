# 电商多 Agent 智能客服系统（简历项目描述）

## 项目定位

面向电商售前/订单/售后场景的多 Agent 客服系统，具备路由、缓存、写操作确认与可复现评测。

## 技术栈

- Python 3.12、FastAPI / Starlette、Pydantic
- httpx（ASGITransport，用于评测与压测）
- Redis（会话历史、会话状态、pending 存储与分布式锁）与 SQLite（本地回退）
- OpenAI 兼容 SDK（DeepSeek，可选真实 LLM）
- Langfuse SDK（可选观测与 dataset，未配置时 no-op）
- pytest、asyncio、标准库（无 numpy/pandas/locust/k6）

## 核心工作

1. **设计并实现多 Agent 路由与工具子集**：规则优先、LLM 兜底、默认 Profile 三级降级；路由类任务通过率从 40.0%（M-03）提升到 100.0%（M-02，+60.0 个百分点，M-04），整体任务通过率从 59.1%（M-17）提升到 100.0%（M-01，+40.9 个百分点，M-22）。
2. **实现归一化消息缓存**：以“稳定前缀哈希 + 归一化消息哈希”为 key，按 Profile 白名单与 TTL 生效；最高并发度下命中率 82.0%（M-05），QPS 从 516.29（M-08）提升到 890.92（M-09，+72.6%，M-06），P95 从 19.5 ms（M-18）变为 19.0 ms（M-19，降低 2.7%，M-07）。以上为 Mock 压测与 10ms 模拟编排条件（COND-01），绝对 QPS 不代表生产容量。
3. **实现服务端两阶段确认与 Redis pending**：写操作先拦截并返回 `needs_confirmation`，确认后执行；Redis 实现跨实例 pending 与分布式锁；错误注入任务通过率 100.0%（M-13）。关闭两阶段确认的对照同样为 100.0%（M-15），说明 Mock 任务集无法量化该安全机制的收益，相关结论只做描述性说明。
4. **建立固定任务集评测与并发压测体系**：27 条任务（M-20）覆盖路由、缓存、错误注入与边界输入，压测总请求 650 次（M-21）；所有对外引用的数字都记录在 `docs/resume/metrics-index.json`（M-01 至 M-23），并标注来源报告与测量条件（COND-01 至 COND-06）。

## 可能的追问与预设回答

1. **“为什么不用 LangGraph？”**  
   答：评测需要在同一进程内按开关关闭模块做对照，且协议不能改；详细取舍与代价见 `docs/resume/decisions.md` 的 D-01。
2. **“缓存为什么不用 embedding？”**  
   答：先保证不返回错误答案，再追求命中率；精确哈希 + 稳定前缀哈希的设计见 D-05 与 D-09。
3. **“Redis 挂了为什么不降级到内存？”**  
   答：pending 分叉会导致重复写操作，写路径优先保证不重复执行；见 D-07。
