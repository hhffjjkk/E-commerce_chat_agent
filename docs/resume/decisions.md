# 技术决策点清单

每条决策都给出当时的约束、可选项、选择、代价与“什么条件下才会换”。
不写“因为我们熟悉 X”，也不写没有代价的决策。

---

### D-01：为什么用自研 Harness 而不是 LangGraph

- **当时的约束**：已有一个可运行的单文件 Agent；需要在不大改业务的前提下加入路由、上下文预算、循环控制、Retry 与评测开关；评测时要求能单独关闭每个模块做对照。
- **可选项**：
  - 选项 1：LangGraph（图编排成熟、社区大、有 checkpoint）
  - 选项 2：手写轻量 Harness（Router / ContextAssembler / LoopController / Retry / Guardrails / ToolRegistry）
- **选择**：选项 2
- **理由**：
  1. 评测需要在同一进程内按开关关闭某个模块（`NMSG_CACHE_ENABLED`、`RETRY_ENABLED`、`ROUTER_STRATEGY`），自研模块的边界可以直接映射到开关；
  2. 现有 `/chat` 与 `/chat/stream` 协议不能变，自研可以在不改变响应结构的前提下插入事件；
  3. 依赖越少，CI 越稳定；项目只需要单 Agent 的有界循环，不需要复杂图状态。
- **代价**：没有内置 checkpoint、断点恢复与可视化；多 Agent 长期任务需要自己补持久化与恢复语义。
- **如果重来**：当出现“跨请求的长任务图、需要断点恢复、需要人工审批节点”时，才值得换成 LangGraph。
- **面试可讲的亮点**：用评测开关倒推架构边界——模块不是按“概念好听”拆，而是按“能否被独立关闭与度量”拆。

### D-02：Router 为什么是“规则优先 + LLM 兜底 + 默认 Profile”

- **当时的约束**：大部分客服消息有明确业务词（订单、物流、退款），但存在模糊表述；无 Key 时也要能跑；路由失败不能中断请求。
- **可选项**：
  - 选项 1：只做规则路由（便宜但模糊消息无法分流）
  - 选项 2：只做 LLM 路由（准确但每次请求多一次模型调用，且不可用时全崩）
  - 选项 3：规则优先、LLM 兜底、默认 Profile 三级降级
- **选择**：选项 3（`ROUTER_STRATEGY=rule_first`）
- **理由**：
  1. 规则命中时零成本、可解释，且能覆盖高频业务词；
  2. 规则低置信时才调用 LLM，控制成本；
  3. LLM 不可用或解析失败时回到默认 Profile，保证请求可完成。
- **代价**：规则表需要维护；规则与 LLM 的判定可能不一致；低置信规则结果仍可能误分流。
- **如果重来**：当规则表维护成本超过 LLM 路由成本，或业务意图需要多轮澄清时，才考虑改为 LLM 优先或分类模型。
- **面试可讲的亮点**：把“路由”当成一个可降级的策略链，而不是一次不可失败的分类调用。

### D-03：写操作为什么要用服务端两阶段确认

- **当时的约束**：退款/取消是高危写操作；模型可能被提示注入或误判；需要审计与幂等。
- **可选项**：
  - 选项 1：只靠提示词要求模型先确认
  - 选项 2：客户端确认弹窗
  - 选项 3：服务端状态机拦截写工具，返回 `needs_confirmation` 与 `action_id`
- **选择**：选项 3
- **理由**：
  1. 提示词可被绕过，状态机不可；
  2. `summary` 由服务端生成，不依赖模型复述，避免伪造；
  3. `action_id` 支持幂等确认、跨请求重试与审计。
- **代价**：多一次工具调用与状态存储；需要处理过期、跨会话、并发确认；客户端交互变复杂。
- **如果重来**：当所有写操作都有强事务与外部审批系统时，可以把确认交给外部审批，但服务端仍需保留最终校验。
- **面试可讲的亮点**：把安全边界放在模型之外——模型只能“请求”，不能“执行”。

### D-04：Pending 用墙钟、循环超时用单调钟

- **当时的约束**：pending 记录可能在多实例间共享；循环超时只在一个进程内比较。
- **可选项**：
  - 选项 1：全部用 `time.monotonic()`
  - 选项 2：全部用 `time.time()`
  - 选项 3：pending 用墙钟，循环/重试用单调钟
- **选择**：选项 3
- **理由**：
  1. `monotonic()` 的起点随进程启动变化，跨实例不可比较，不能用于共享过期时间；
  2. 循环超时只在本进程内判断，单调钟不受系统时间回拨影响，更适合；
  3. 墙钟判断增加 5 秒容差，吸收 NTP 跳变，但不改变 `expires_at` 本身。
- **代价**：墙钟仍可能跳变；容差让过期判断略晚，需要文档说明。
- **如果重来**：如果引入统一的授时服务或逻辑时钟，可以进一步减少墙钟不一致，但不会改用单调钟做跨实例比较。
- **面试可讲的亮点**：同一个“时间”概念，在不同作用域要用不同时钟，这是分布式系统的基本功。

### D-05：为什么是归一化消息缓存，而不是 embedding 语义缓存

- **当时的约束**：缓存必须可解释、可失效、不能把不同商品/订单的答案混用；没有稳定的 embedding 服务与向量库。
- **可选项**：
  - 选项 1：embedding 语义缓存（召回高，但可能误命中）
  - 选项 2：归一化精确哈希缓存（稳定前缀 + 归一化消息）
  - 选项 3：不缓存，只做并发优化
- **选择**：选项 2
- **理由**：
  1. 命中条件是两个哈希完全相等，不会把“退货政策”和“退款进度”混为一条；
  2. key 包含稳定前缀哈希，Profile 或工具 schema 变化会自动失效；
  3. 无额外模型与向量库依赖，评测可复现。
- **代价**：召回率有限，同义句不命中；长消息与纯数字不缓存；收益依赖重复流量。
- **如果重来**：当同义问法占比高、且有可靠的相似度阈值与人工抽检机制时，才考虑加一层语义缓存，并保留精确缓存作为第一层。
- **面试可讲的亮点**：缓存的第一目标是“不返回错误答案”，第二目标才是命中率。

### D-06：Retry 为什么默认关闭

- **当时的约束**：Mock 与真实 LLM 都可能失败；重试能提升成功率，但会放大故障与延迟；写操作不能重试。
- **可选项**：
  - 选项 1：默认开启重试
  - 选项 2：默认关闭，按部署显式开启
- **选择**：选项 2（`RETRY_ENABLED=false`）
- **理由**：
  1. 重试会把下游故障放大（重试风暴），默认关闭更安全；
  2. 写操作永不重试，读工具重试需要单独的幂等白名单；
  3. 评测可以在需要时显式开启，对照成本可控。
- **代价**：默认配置下暂时性错误的成功率较低；需要运维显式调参。
- **如果重来**：当上游提供明确的限流反馈与幂等保证、且团队有重试预算监控时，可以把读请求重试默认打开。
- **面试可讲的亮点**：默认值应该选择“故障时不会更糟”的那一侧。

### D-07：Redis pending 不可达时为什么显式失败

- **当时的约束**：pending 是写操作的唯一状态来源；多实例部署下不能出现“两个实例各自记一份”。
- **可选项**：
  - 选项 1：Redis 故障时回退内存，保证可用
  - 选项 2：显式失败，要求用户重新发起
- **选择**：选项 2
- **理由**：
  1. 回退内存会让 pending 分叉，可能重复执行写操作；
  2. 显式失败可观测、可告警，用户重试的成本低于重复退款；
  3. 与 Redis 会话存储的 `REDIS_FALLBACK_TO_MEMORY=false` 默认口径一致。
- **代价**：Redis 故障期间写操作不可用；需要运维预案。
- **如果重来**：如果写操作有外部幂等键与事务日志，可以考虑降级，但仍需保证“同一 action 只执行一次”。
- **面试可讲的亮点**：可用性不是无条件优先，写路径要优先保证不重复执行。

### D-08：压测为什么用 ASGITransport in-process

- **当时的约束**：需要可重复、可在 CI 运行的压测；不能引入 locust/k6 或额外端口；重点是缓存与编排的相对收益。
- **可选项**：
  - 选项 1：启动 uvicorn + 真实 HTTP 客户端
  - 选项 2：httpx `ASGITransport` 直接压 ASGI app
- **选择**：选项 2（默认）
- **理由**：
  1. 去掉端口、进程与网络噪声，差异更容易归因到业务模块；
  2. 与步骤 1 的评测共用一套工具链；
  3. CI 不需要额外服务。
- **代价**：测不到真实网络栈、TLS、代理与多进程；绝对 QPS 不代表生产容量。
- **如果重来**：当需要容量规划或验证网关/多 worker 行为时，必须补真实网络压测。
- **面试可讲的亮点**：先控制变量得到可信的相对结论，再决定是否为绝对容量投入真实环境。

### D-09：`stable_prefix_hash` 为什么是缓存 key 的一部分

- **当时的约束**：不同 Profile 有不同系统提示与工具 schema；如果只按消息哈希，pre_sales 的答案可能被 order 命中。
- **可选项**：
  - 选项 1：只用消息哈希
  - 选项 2：消息哈希 + Profile 名称
  - 选项 3：消息哈希 + 系统提示与工具 schema 的稳定哈希
- **选择**：选项 3
- **理由**：
  1. 只要 Prompt 或工具 schema 变化，旧缓存自动失效，不需要手工清缓存；
  2. 按 Profile 隔离，避免跨业务域串答案；
  3. 哈希可计算、可解释，评测中可以断言不同 Profile 的哈希不同。
- **代价**：每次查缓存前要计算稳定前缀哈希，增加少量 CPU；schema 变化会导致缓存整体失效。
- **如果重来**：如果前缀计算成为瓶颈，可以按 Profile 缓存哈希值，但仍需在 schema 版本变化时失效。
- **面试可讲的亮点**：把“缓存正确性”编码进 key，而不是依赖人工清理。

### D-10：为什么在 Mock 压测中注入 10ms 模拟编排耗时

- **当时的约束**：MockLLM 是本地规则引擎，回复只要几十微秒；in-process 框架开销约 1ms，缓存收益会被完全淹没；验收要求对比缓存前后的 QPS。
- **可选项**：
  - 选项 1：不注入，接受 Mock 下 QPS 差异在噪声内
  - 选项 2：注入固定小延迟，代表真实 LLM 编排成本，并在报告披露
  - 选项 3：直接用真实 LLM 压测
- **选择**：选项 2（`MOCK_LLM_ORCHESTRATION_MS=10`）
- **理由**：
  1. 让“跳过 LLM 编排”的收益在 Mock 下可测量、可复现；
  2. 延迟只作用于 cache-miss 请求，且远低于真实 LLM 的数百毫秒；
  3. 报告运行信息与摘要都披露该假设，避免把绝对 QPS 当生产容量。
- **代价**：绝对 QPS 是模型化结果，不能用于容量规划；读者必须同时看 caveat。
- **如果重来**：有 API Key 与稳定测试环境后，应改用真实 LLM 压测，并保留 Mock 结果仅作相对回归。
- **面试可讲的亮点**：当测量工具的分辨率低于被测差异时，要么改工具，要么明确建模并披露假设，不能假装数字是真的。
